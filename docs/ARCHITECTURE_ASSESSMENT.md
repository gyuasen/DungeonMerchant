# DungeonMerchant 構造評価

このプロジェクトのアーキテクチャを、良い点・悪い点を同じ密度で評価する。
評価日：2026-07-30 / 対象：Assets/Proiject（Scripts 152ファイル、Tests 75ファイル）

**評価方針**：印象ではなく実測に基づく。「失敗が多いはず」という前提も検証対象とする——実際に測った結果、その前提は**部分的にしか正しくなかった**。

---

## 総合評価

**個人開発のゲームプロジェクトとしては、平均を明確に上回る。**

構造的な弱点は確かに存在し、そのうち1つ（UI層の肥大）は深刻。ただし**弱点の性質が「よくある失敗」とは違う**。典型的な個人開発の失敗は「動けばいい、テストなし、後から手が付けられない」だが、このプロジェクトは逆方向に振れている——**テストと分離への投資は実在し、機能している**。問題は投資が**UI層に届かなかった**ことであり、無かったことではない。

| 領域 | 評価 | 根拠 |
|---|---|---|
| テスト戦略 | **A** | 713件/12,096行。対象選定が的確 |
| ドメインロジックの分離 | **B+** | 23サービス抽出、38ファイルがUnity完全非依存 |
| セーブ設計 | **B+** | v36まで移行を維持、永続ID採用 |
| パフォーマンス対応 | **B** | 計測起点。ただし対症療法的 |
| 依存関係管理 | **C** | FindObjectOfType 134箇所、asmdef 1枚 |
| UI層の構造 | **D** | 単一クラス10,128行、共有フィールド271 |

## 評価できる点

### 1. テスト戦略 — このプロジェクト最大の強み【A】

**713件のテスト、12,096行**。プロダクションコードに対して**29%のテストコード比率**は、個人開発では極めて高い。

ただし数より重要なのは**対象選定**。上位ファイルを見ると、テストが「書きやすい所」ではなく「壊れると痛い所」に置かれている：

| テストファイル | 件数 | 守っている対象 |
|---|---|---|
| `TownAvailabilityParityTests` | **58** | リファクタリング前後の等価性 |
| `BattleSkillResolverTests` | 42 | 戦闘スキル解決（1,120行の複雑ロジック） |
| `DungeonEquipmentSetBonusTests` | 27 | セット装備ボーナス（仕様が入り組む） |
| `WorldMapServiceTests` | 24 | マップ解放判定（セーブ復元と絡む） |
| `BalanceExpansionDefinitionTests` | 22 | バランス定義の整合 |

**特筆すべきは `TownAvailabilityParityTests` の58件**。これは機能テストではなく**パリティテスト**——リファクタリング前の実装と後の実装が、810通りの組み合わせで同じ結果を返すことを検証している。

これは「テストを書いた」のではなく「**安全にリファクタリングするための足場を組んだ**」ということ。手段と目的の関係を理解している証拠であり、実務のレガシー改修で最も求められる考え方に一致する。

**加えて、テストが実際に重大バグを捕まえた実績がある**。初期借金5000万への変更後、`5000万 × 75` が int を溢れて返済判定が壊れた件（Q2-3）。これは**後発の変更が既存ロジックを壊す**類のバグで、単体のコードレビューではまず見つからない。回帰テストが継続的に回っていたから捕捉できた。**テスト投資が具体的に回収された事例**として明確。

### 2. ドメインロジックの分離は「掛け声」ではなく実在する【B+】

前回の文書（REBUILD_RETROSPECTIVE）で「Unity非依存層は規約でしかなく強制力がない」と書いたが、**これは公平性を欠いていた**。強制力がないのは事実だが、**規約は実際に守られている**。

実測：**152ファイル中38ファイル（25%）が `MonoBehaviour` も `using UnityEngine` も含まない完全な純粋C#**。

フォルダ別の純度：

| フォルダ | 純粋 / 総数 | 評価 |
|---|---|---|
| Item | 8 / 17 (47%) | 良好。値オブジェクトが適切に分離 |
| Battle | 5 / 15 (33%) | 良好。`DamageResolver` `BattleStatusEffectService` など |
| Core | 3 / 14 (21%) | `WorldMapService` `GameSaveData` は分離済み |
| Mercenary | 3 / 14 (21%) | `HealingCostService` `TrainingCostService` |
| **UI** | **14 / 66 (21%)** | UIですら2割が純粋（`BattlePageUI` 等） |

`EquipmentQuality` `ItemRarity` `EquipmentSlot` のような列挙・値型がUnityから独立し、`HealingCostService` `TrainingCostService` `TownServicePolicy` のような**料金・ポリシー計算が純粋関数として切り出されている**。これは意識的な設計判断の結果であり、偶然ではない。

**23個のサービスクラス**（`*Service` `*Calculator` `*Resolver` `*Builder` `*Formatter` `*Policy`）が抽出されている点も、責務分離への継続的な取り組みを示す。

### 3. セーブ設計 — 個人開発として異例の水準【B+】

version **36** まで後方互換を維持。個人開発なら「セーブを消してくれ」で済ませられる場面を、36回すべて移行コードで対応している。

構造も適切：

- 移行が機能単位の関数に分割（`MigrateDebt` `MigrateQuestLocations` `MigrateStoryProgress` …）
- 各関数が `sourceVersion` を見て自分の担当だけ処理 → 新規追加時に既存を読まなくてよい
- **永続IDによる参照解決** → アセット再編成とセーブ互換を切り離した
- `version > CurrentVersion` はそのまま返す → 新版データを旧版が破壊しない

最後の1点は**見落とされやすい配慮**で、ここまで手が回っているのは評価に値する。

### 4. パフォーマンス対応が計測起点である【B】

3件の最適化コミットすべてが「推測ではなく計測」から始まっている。特にボス戦フリーズの件は、**症状（戦闘中）と原因（倉庫UIの `FindObjectOfType` ループ）が全く別の場所**だった。推測で戦闘コードを触っていれば時間を浪費していたところを、Profilerで実測して9行の修正で解決している。

`BattleRewardService` の最適化で**乱数消費順の不変性を保証**した点も見識が高い。ループの回し方を変えると乱数の引き順が変わり、同じシードで結果が変わる——この落とし穴を認識し、「観測可能な振る舞いを1ミリも変えない」を最適化の前提条件として守っている。

**Bに留めた理由**は後述（対症療法に留まっている）。

## 問題点

### 1. UI層の肥大 — 最も深刻な構造的欠陥【D】

`SimpleMercenaryHireUI` は19ファイルにpartial分割されているが、**合計10,128行**。分割は物理的なものに留まり、**論理的には依然として単一の巨大クラス**。

決定的な問題は**共有フィールド/メソッド宣言が271個**あること。partial は同一クラスなので、これら271個の状態が**19ファイル全域から無制限にアクセス可能**。つまり：

- `SimpleMercenaryHireUI.Economy.cs` を読むだけでは、そこで触る状態が他のどこから書き換えられるか分からない
- カプセル化の境界が存在しない（`private` が事実上 `internal` として機能している）
- 1つの状態変更の影響範囲が10,128行全体

**UIフォルダはScripts全体の51%（21,268行）**を占め、ロジックがUI層に引き寄せられ続けた結果を示している。

**ただし公平を期すと**：ここには「巨大クラスを解体しようとした形跡」が明確にある。`EconomyController` `CharacterEquipmentController` `DailyResultController` などのController抽出は実際に進んでおり、抽出済みクラスは**コンストラクタ注入で依存を明示している**（`EconomyController` は10個の依存を受け取る）。方向は正しく、**到達距離が足りていない**というのが正確な評価。

### 2. 依存関係が型検索で解決されている【C】

`FindObjectOfType` が **134箇所 / 30ファイル**。

| ファイル | 件数 |
|---|---|
| `SimpleMercenaryHireUI.cs` | 20 |
| `SaveManager.cs` | **18** |
| `ProgressionManager.cs` | 8 |
| `OnboardingGuideController.cs` | 7 |

**`SaveManager.cs` の18箇所が構造的に最も問題**。セーブはドメイン状態の永続化であり、本来シーン構成から独立すべき層。そこがシーン上のオブジェクトを型検索で掴んでいるということは、**セーブ処理がシーン構成に暗黙依存している**。

問題は性能だけではない：

1. **依存が不可視** — クラス定義を見ても何に依存するか分からず、全メソッドを読む必要がある
2. **テスト不能** — シーンが必要になり、EditModeテストに持ち込めない
3. **fake-null 事故** — `StoryProgressManager` の購読漏れ（明示注入で対処済み）は暗黙解決が原因

そしてQ3-1のフリーズは、この134箇所の**うち1箇所**が原因だった。**残り133箇所は同種のリスクを抱えたまま**。この事実が、パフォーマンス対応をBに留めた理由——**個別の症状は正しく直したが、症状を生む構造は残っている**。

### 3. アセンブリ境界の不在【C の根本原因】

Runtime asmdef が **1枚**。全152ファイルが単一アセンブリに同居し、`Core` → `UI` の参照も、その逆も、コンパイラは一切警告しない。

前述の通り、分離の規約は**実際には守られている**（純粋C# 25%）。しかしそれは**開発者の注意力のみで支えられている**。`SaveManager` の18箇所が示すように、注意力は一箇所で切れれば崩れる。

`Domain` アセンブリを切って `"noEngineReferences": true` を立てれば、`UnityEngine` を参照した瞬間コンパイルエラーになる——**規約が物理的制約に変わる**。現状はその安全装置が無い。

### 4. バランス数値の散在【中程度】

`Balance` フォルダに**1ファイルのみ**。数値の大半がコード内リテラルか個別ScriptableObjectに散在している。

この構造が借金額変更（1億→5000万）の修正コストを押し上げた。連動してチュートリアル文言・物語進行閾値・別動隊の収益前提まで波及している（コミット履歴に残存）。

**「この数値を変えたら何が壊れるか」が把握できない構造**になっている。

## 評価の要点：この構造をどう解釈すべきか

### 失敗の性質が「よくある失敗」とは異なる

個人開発の典型的な失敗は**「テストなし・分離なし・後から手が付かない」**。このプロジェクトは違う。

- テスト713件は実在し、パリティテストという高度な使い方までしている
- 純粋C# 25%、サービス23個の抽出は意識的な設計の産物
- セーブ移行v36は多くの商用個人開発より丁寧

**問題は「やらなかった」ではなく「UI層に届かなかった」**。ドメイン層（Battle, Item, Mercenary）には分離とテストが行き渡っている一方、UI層だけが10,128行の塊として残った。

### なぜUI層だけ取り残されたか

構造的な理由がある。**UIはUnity APIとの結合が最も強く、切り出すコストが最も高い**。ドメインロジックは純粋関数にすればテストできるが、UIは `Button` `RectTransform` に触れる限りテストできない。

さらにこのプロジェクトはUI構築を全てコードで行っている（`new GameObject`/`AddComponent` が248箇所、Prefabsフォルダは空）。これは**Unityのシーン/Prefabがマージ困難というリアルな問題への対処**でもあり、一概に誤りとは言えない。ただし結果としてUI層に大量のコードが集中した。

### 開発プロセスとしての評価

コミット履歴（113件）を見ると、**「動くものを作る → 痛みが出た箇所を直す」というサイクルが一貫している**。仕様が固まらない個人開発では合理的な進め方であり、実際に借金額・物語進行・別動隊など仕様は何度も変わっている。先に構造を固めていれば作り直しになっていた。

**反省点があるとすれば、「痛みが出てから直す」を続けた結果、直すタイミングを一度も意識的に作らなかったこと。** `FindObjectOfType` が134箇所まで増えたのは、1箇所ずつ足す判断が毎回は正しくても、全体として管理されなかったから。

## 就活での提示方法

**この構造は隠すべきものではなく、説明できれば強い材料になる。**

面接で「設計の弱点は？」と聞かれたときの推奨回答：

> 最大の弱点はUI層です。`SimpleMercenaryHireUI` は19ファイルにpartial分割していますが合計10,128行あり、共有フィールドが271個あるため、論理的には巨大クラスのままです。
>
> 一方でドメイン層は分離できていて、152ファイル中38ファイルがUnity完全非依存、テストは713件あります。**同じ努力をしたのに層によって結果が違った**のは、UIがUnity APIとの結合が強く切り出しコストが高いからです。
>
> 学んだのは、**アセンブリ分割のような「構造を強制する仕組み」を先に入れておくべきだった**ということです。規約は実際25%の純粋C#として守られましたが、`SaveManager` に `FindObjectOfType` が18箇所入り込んだように、注意力だけでは一箇所で崩れます。

この答え方なら、**弱点を認識していること**と**原因を構造的に説明できること**が同時に伝わる。弱点を挙げるだけでも、良い点を並べるだけでも足りない——両方を実測値で語れることが評価される。

## 結論

**個人開発として明確に平均以上。技術的な判断力を示す証拠が複数ある。**

- テスト713件とパリティテストの発想は、実務のレガシー改修で最も価値ある能力に直結
- 計測起点のパフォーマンス対応、乱数消費順の保存は見識の高さを示す
- セーブ移行v36は運用視点を持っている証拠

**同時に、UI層の10,128行と `FindObjectOfType` 134箇所は実在する負債であり、擁護すべきではない。**

ただしこの負債は**「技術力の不足」ではなく「投資配分の偏り」の結果**。ドメイン層に投資できた事実が、UI層にも同じことができた可能性を示している。実際、Controller抽出は始まっており方向は正しい。到達していないだけ。

**「多くの失敗がある」という当初の見立ては、実測の結果、正確ではなかった。** 失敗は多くはなく、**深い失敗が1箇所（UI層）と、構造的な脆弱性が1箇所（依存管理）**。他の領域は個人開発の水準を上回っている。
